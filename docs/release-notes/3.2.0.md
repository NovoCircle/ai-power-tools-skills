Skills bundle 3.2.0 for AI Power Tools for Sparx EA.

Requires server **3.0.0** or newer. The floor is enforced all or nothing: an older server receives no files and an error naming the version it needs.

21 entries. **No skill content changed in this release** — the manifest regenerates byte-identical to 3.1.0. What changed is how the skills can be delivered.

## New: the skills ship as a plugin

Until now the only way to install these skills was the `install_skills` MCP tool, which writes to `~/.claude/skills`. That directory is read by the Claude Code surfaces — the CLI, the desktop Code tab, VS Code — and by nothing else. Claude Desktop's chat and Cowork never read it, so those surfaces had no skills at all.

Plugins are the one mechanism every surface loads. This release adds a plugin, `ai-power-tools`, built from the same tree as the bundle, so one set of skill files now serves every surface. Nothing is copied or transformed between the two channels and they cannot drift.

`install_skills` is unchanged and keeps working. Existing installs need no action.

## Installing

**Claude Code (CLI, desktop Code tab, VS Code)**

```
claude plugin marketplace add NovoCircle/ai-power-tools-skills
claude plugin install ai-power-tools@novocircle
```

**Cowork / Claude Desktop**

Download `ai-power-tools.plugin` from this release and upload it in Claude Desktop.

Cowork runs in a cloud sandbox that attaches back to Claude Desktop on your machine: the desktop mounts the plugin into the sandbox and proxies its MCP servers to the host, so Enterprise Architect stays local. The workstation still needs Claude Desktop, the `.mcpb` extension and a working EA install — a cloud Cowork session relocates the conversation, not EA.

## Enterprise deployment

Two artifacts reach a workstation, and they version separately: the `.mcpb` MCP server (per machine, needs local EA) and this skills plugin.

For a managed fleet, declare the marketplace and the plugin in the admin-controlled settings source and every machine picks it up with no user action.

Windows, either of:

- the `HKLM\SOFTWARE\Policies\ClaudeCode` registry key
- `C:\Program Files\ClaudeCode\managed-settings.json`

macOS and Linux: `/etc/claude-code/managed-settings.json`

```json
{
  "extraKnownMarketplaces": {
    "novocircle": {
      "source": {
        "source": "github",
        "repo": "NovoCircle/ai-power-tools-skills",
        "ref": "v3.2.0"
      }
    }
  },
  "enabledPlugins": {
    "ai-power-tools@novocircle": true
  }
}
```

Two things to know:

- A marketplace on a network location **must** be declared in user or managed settings. Project and local scope are refused for network sources, so managed settings is the correct admin-trusted home.
- `ref` pins the fleet to a git ref. Pin it to a release tag wherever an unreviewed skill change would be unwelcome; omit it to track the default branch.

### How updates reach each route

| Route | How a new version arrives | Automatic |
|---|---|---|
| Marketplace, per user | `claude plugin marketplace update novocircle` then `claude plugin update ai-power-tools` | No |
| `.plugin` upload | Re-upload the new file; nothing prompts | No |
| Managed settings, unpinned | Marketplace refresh | Yes |
| Managed settings, pinned | Bump `ref` in the policy | Yes, once bumped |

A plugin update is staged, not hot-swapped: **a restart is required to apply it**.

`.plugin` uploads are per machine and do not sync across a user's devices. Treat that route as a pilot mechanism; use managed settings for a fleet.

### Two constraints worth knowing before they bite

- **A required `user_config` field with no default breaks sandboxed Cowork.** When the desktop proxies an MCPB server to the host it drops any server whose manifest declares a `user_config` entry that is `required: true` with no `default` — silently, with no user-facing error. The current server manifest has no such field and must keep none.
- **Policy can block third-party marketplaces outright**, which takes the managed-settings route off the table and forces the organization's own provisioning instead.

Full detail in `docs/enterprise-deployment.md`.

## Verifying an install

```
claude plugin list
claude plugin details ai-power-tools
```

Expect `ai-power-tools@novocircle` enabled at 3.2.0, and `Skills (19)`. `_shared` is correctly not among them — it carries no `SKILL.md` and ships only so the skills' relative links resolve.

Installed with `install_skills`; the installer verifies every file against `manifest.json` and refuses any whose bytes do not match.
