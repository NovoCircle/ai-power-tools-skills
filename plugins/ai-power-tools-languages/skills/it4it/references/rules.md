# IT4IT 3.0 rules, read from the public draft

Generated from `language.yaml` (`constraints`). Do not edit by hand; change the language file and regenerate.

Each rule has a stable id of the form `IT4IT-<CAT>-nnn`. The number never changes once assigned. A rule that is retired keeps its id and is marked withdrawn rather than reused.

The standard states its requirements in prose only, with "shall", "should", "may" and "can". It defines no constraint language. The rules below are our statements of those sentences, in our own words, with the clause they come from.

## Strength

| Strength | Meaning |
|---|---|
| must | The standard states it with "shall", "must" or a prohibition. A model, tool or practice that breaks it does not conform to the reference architecture. |
| should | The standard recommends it ("should"). Breaking it is a warning. |
| note | The standard states an option ("may"), a possible behavior ("can") or a plain fact. It is advice and is not checkable on its own. |

Where a rule says "the component shall ...", it describes what a system that plays that functional component supplies. It does not say what a model must contain; those rules have `checkable: none`.
